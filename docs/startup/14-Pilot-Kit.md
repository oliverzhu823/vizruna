# Vizruna v0.1 试点执行包

本执行包用于 3–5 名真实内部或友好客户用户。它提供计划、脚本、反馈模板和 Go/No-Go 标准，不预先填写或虚构用户结论。

## 1. 试点目标

验证四个问题：

1. 非开发维护人员能否独立安装并完成首次 Agent 任务。
2. 国际 Provider 代理与中国 Provider 直连能否共存且不影响其他软件。
3. Worktree 和多 Agent 是否让并行任务更安全、更容易判断结果。
4. 出错时，用户能否依靠错误提示、诊断和恢复能力继续工作。

## 2. 建议样本

选择 3–5 人，覆盖：

| 用户类型 | 建议人数 | 重点 |
| --- | ---: | --- |
| 企业业务/产品人员 | 1 | 首次学习成本、文案、信任 |
| 软件工程师 | 1–2 | Git、Review、Worktree、测试证据 |
| IT/实施人员 | 1 | 安装、代理、诊断、数据边界 |
| 技术管理者 | 0–1 | 多 Agent 可观察性和服务价值 |

至少一人的机器使用需要代理的国际 Provider，至少一人使用中国 Provider 直连。不要只选择项目开发者本人。

## 3. 试点前置

- 仅使用已通过 G8 的签名、公证候选版本。
- 使用可重建的测试仓库。
- 使用限额测试 Key。
- 记录 macOS、机器型号、网络/代理客户端和 Provider。
- 说明本地权限模型：Agent 和扩展可能执行命令、读写项目；产品不是操作系统沙箱。
- 取得诊断日志和屏幕录制的明确同意。

## 4. 每位用户的 60–90 分钟流程

主持人只读题，不代替用户操作。

### 场景 A：安装与首次任务

1. 从内部发布页下载并校验 DMG。
2. 安装、启动、切换语言。
3. 打开测试项目。
4. 让 Agent 只读分析项目并说明启动方式。

记录：是否需要帮助、首次有效回复耗时、卡点和误解。

### 场景 B：双 Provider 路由

1. 新建 HTTP 或 SOCKS5 代理 Profile；如企业内网需要，填写该 Profile 的 `NO_PROXY`。
2. 国际 Provider 选择 Profile 并测试。
3. 中国 Provider 选择 direct 并测试。
4. 各执行一次短模型请求。
5. 检查代理客户端和其他应用设置未被修改。

记录：路由是否可理解、诊断是否足以定位失败、真实请求结果。

### 场景 C：代码修改与证据

1. 让 Agent 修改一个小功能。
2. 要求运行测试。
3. 在 Review 查看文件和 diff。
4. 判断“已完成”是否有退出码和文件证据。

记录：用户是否能区分模型声明与系统证据。

### 场景 D：Worktree 与多 Agent

1. 创建两个独立子任务。
2. 查看任务树、排队、状态和 Worktree。
3. 取消其中一个子任务。
4. 保留证据并安全回收可删除的 Worktree。

记录：是否理解隔离、取消、脏状态和强制删除风险。

### 场景 E：恢复与诊断

1. 在安全的测试任务中模拟中断或退出。
2. 重启应用并检查任务没有被误报成功。
3. 预览并导出诊断包。
4. 创建元数据备份。

记录：用户是否知道下一步，诊断包是否出现敏感数据。

## 6. 反馈访谈模板

每题先让用户自由回答，再追问具体事实：

1. 你以为这个产品能做什么？实际哪里不同？
2. 从安装到第一次有效结果，最费力的一步是什么？
3. Provider 路由中的 direct/system/profile，你如何理解？
4. 遇到失败时，你看了哪条信息？它是否告诉你下一步？
5. 你是否信任“任务完成”？你依据的是模型文字、文件还是测试证据？
6. Worktree 和任务树帮助了你，还是增加了概念负担？
7. 哪个功能会让你愿意在真实工作中继续使用？
8. 哪个问题会阻止你向同事推荐？
9. 你认为公司需要哪些治理能力，而本地工作台当前没有？
10. 如果这是企业 AI 转型服务包的一部分，最需要的陪跑服务是什么？

- 安装容易度：
- 首次配置容易度：
- 代理路由清晰度：
- Agent 结果可信度：
- 错误恢复信心：
- 日常使用意愿：

## 7. 问题分级

| 级别 | 定义 | 发布动作 |
| --- | --- | --- |
| S0 | 数据损坏、凭据泄露、代码误删、系统代理被修改 | 立即停止试点和发布 |
| S1 | 无法安装、无法完成首次模型调用、核心任务无限运行 | No-Go，修复后重测 |
| S2 | 有明确规避方案但严重影响效率或理解 | 指定负责人和下一版本，产品负责人决定 |
| S3 | 文案、样式或低频体验问题 | 进入 Backlog |

任何 S0/S1 都不能用“已知问题”标记为通过。

## 9. 试点 Go/No-Go

Go 条件：

- 至少 3 名真实用户完成全部 P0 场景。
- 试运行负责人另行完成至少 20 次真实 Agent 启动，成功率不低于 95%，并在
  至少一次 4 Agent 并发期间确认 UI 可交互、状态无串线。
- 100% 完成安装和两类 Provider 路由。
- 无开放 S0/S1。
- 核心任务成功率达到产品负责人预先确认的阈值。
- 诊断包无敏感信息。
- 开放 S2 均有负责人、规避方案和计划版本。

No-Go 条件：

- 签名/公证或干净安装未通过。
- 代理路由影响其他应用或发生流量误路由。
- 用户数据、Git 或会话发生不可恢复损坏。
- 结果缺少可验证证据，用户无法判断是否完成。

试点负责人完成汇总后，在 M5 报告附上记录位置、问题列表和签字决策。未执行的模板不能算作 M5-08 通过。

完成每位用户记录后，把证据引用和通过状态填写到本地
`release-evidence/<version>.json` 的 `pilot.participants`；只记录编号、角色、
结果和内部引用，不复制访谈原文、屏幕录制或客户项目内容。运行：

```bash
npm run release:evidence:status
```

脚本会检查 3–5 人、角色覆盖、A–E 场景、双 Provider、S0/S1、S2 处置和
非开发者参与条件。正式 Tag 前还必须由 `npm run release:evidence:check`
与其他发布证据一起通过。
